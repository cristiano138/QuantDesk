# QuantDesk 发展建议与优化路线图

> 审阅日期：2026-11-06（北京时间）。代码基线：`5f939df`。
> 本文记录本轮代码审阅、隔离复现和后续实施方案；“建议”“验收目标”均不表示功能已经实现。
> 当前边界以 `AGENTS.md` 为准：本地运行、策略隔离、订单三道闸、港股仅模拟、盯盘接口无交易入口。
>
> 2026-11-06 后续实施：已经落地的首批修复、验证和剩余问题见 `docs/优化执行记录.md`。
> 下文 F01–F10 保留最初审阅现场，不代表当前版本仍原样存在全部缺陷；阅读进度见 `docs/阅读覆盖清单.md`。

## 1. 发展判断

项目已经有行情、通道注册、回测、模拟撮合、策略 IPC、对账、桌面入口和移动端，值得继续沿用现有技术栈。下一阶段的主要价值来自订单与账本正确、研究结果可复现、版本能够完整交付。

建议将产品主线定为：**个人本地量化工作台——看懂行情，形成规则，验证规则，持续模拟，按前置条件接入 QMT。**

最先打磨三个连续场景：

1. 每日复盘：自选与条件筛选 → 行情来源及新鲜度 → 信号解释 → 保存当日观察记录。
2. 策略研究：模板或自编策略 → 固定数据与参数回测 → 样本外验证 → 生成可重复的研究报告。
3. 模拟跟踪：相同策略进入模拟盘 → 比较预期信号、委托与实际模拟成交 → 用差异解释结果。

QMT 仍是主力交易通道；在线核对、真实账户演练维持单独的用户在场流程。近期研发资源优先投入下面的 P0/P1 项，之后再扩充数据源、策略数量和界面功能。

## 3. 按优先级处理的问题

### F01 · P0：确认订单时缺少最终校验，确认内容没有绑定通道

依据：`quantdesk/engine/riskgate.py:143`、`quantdesk/engine/riskgate.py:408`。

`submit()` 会校验规则并进入待确认；`confirm()` 取出订单后重新解析当前通道，只检查通道存在和连接状态，随后提交。这里没有重新检查全局模拟盘开关、资金、持仓、风控热参、确认截止时间，也没有核对通道是否仍是最初展示的通道。

临时库与假券商复现：

| 待确认期间的变化 | 当前真实输出 | 修复后的验收要求 |
| --- | --- | --- |
| `simulation_only` 切回 True | 仍调用假实盘券商 1 次，返回 `submitted` | 不再发往实盘，原确认单明确失效 |
| 可用现金降到 0 | 仍调用假实盘券商 1 次 | 重新校验资金并拒绝 |
| 通道从 A 切到 B | A 调用 0 次，B 调用 1 次 | 原单失效，重新展示并确认新通道 |
| 确认窗口已过期、清理线程尚未处理 | 仍返回 `submitted` | `confirm()` 当场核对截止时间并作废 |

最后一项通过停止后台清理线程、将计时起点前移 20 秒模拟调度延迟，证明确认入口依赖后台清理；并不表示正常运行时每笔超时单都会放行。

实施：给待确认记录增加持久化确认上下文，包含模式、账户、通道、规则版本、UTC 截止毫秒；确认时原子检查状态与截止时间，再做最新规则校验。开关或通道变化使原确认失效。重启后仍保留记录，但不得无条件把已过期窗口再延长 10 秒。

同时补订单请求幂等：`quantdesk/services/trading.py` 每次调用会生成新订单 ID，接口超时后重发可能形成第二笔委托。由调用方提供请求键，服务端按账户与请求键建立唯一约束；同键不同参数返回冲突。最终校验还要结合资金、可卖量的预占，覆盖两笔并发请求都读到同一份余额的情形。

### F02 · P0：一次成交没有使用同一个数据库事务

依据：`quantdesk/adapters/brokers/paper_broker.py:202`，以及 `quantdesk/store/repo.py:120`、`:181`、`:588`。

模拟成交依次写成交、资金、订单、持仓；这些仓储函数各自提交。已经做到的“先写后广播”需要进一步落实为“同一业务变化原子提交，再广播”。

在成交已写入后，向 `account_set()` 注入异常，真实回读为：

```text
error=injected_account_write_failure
persisted_trades=1
persisted_cash=1000000.0
memory_cash=998994.9
persisted_order_status=submitted
persisted_filled_volume=0
```

实施：增加接收同一 Session 的成交结算事务，统一保存成交、费用、资金、订单累计成交量和持仓；事务失败不能留下半笔账，内存状态也要恢复或从已提交状态重载。不要在持有数据库写事务期间等待外部券商网络调用。

券商执行与 SQLite 无法合成一个本地事务：先持久化提交意图；结果不明时记录待核对状态并向券商查询，不自动重发。回报按账户、通道、券商成交号去重。需要保证断电后事件可补发时，可在同一事务增加 outbox，再由事件分发器处理。

现有库使用 WAL + `synchronous=NORMAL`。应区分进程崩溃恢复与系统断电持久性，在交易账本上评估 `FULL` 并测量延迟。SQLite 的原子提交范围是单个事务；`NORMAL` 在系统故障时的持久性也有明确限制，见[原子提交说明](https://www.sqlite.org/atomiccommit.html)、[同步级别说明](https://www.sqlite.org/pragma.html#pragma_synchronous)。

### F03 · P0：模拟与实盘缺少持久化隔离维度

依据：`quantdesk/store/models_db.py` 的订单、成交、账户表；`quantdesk/adapters/brokers/paper_broker.py:250`。

订单与成交表没有账户、交易模式、通道字段；账户状态固定使用 `id=1`。`PaperBroker._restore()` 会回放成交表里的全部成交，而不是只读取当前模拟账户的成交。

隔离复现：向临时库写入一笔带 `broker_trade_id` 的假外部成交，再启动模拟券商，得到 `paper_position_volume=100`，模拟现金仍为 `1000000.0`。这说明当前结构不能可靠区分两种账本。

实施：通过增量迁移增加 `account_id / trading_mode / broker_channel`，资金、持仓、订单、成交、挂单恢复、对账和列表查询都带相同作用域。原有核心模型字段与适配器合同保留，新增信息使用向后兼容字段或关联表承载。不得把“所有不认识的旧成交”直接认领成模拟成交；旧库升级前备份，来源无法判断的记录单列待认领。

验收：同库预置模拟与假实盘成交，反复切换模式并重启；模拟现金、持仓、挂单完全不受假实盘成交影响，对账也不跨账户比较。

### F04 · P0：电脑端缺少按币种记账，费用校验与撮合也有差异

依据：`quantdesk/adapters/brokers/paper_broker.py:181`、`quantdesk/engine/riskgate.py:248`、`QuantDesk-App/手机看盘.html:533`。

手机模拟盘已有 CNY/USD/HKD 三个钱包；电脑端仍是一个 `cash`，账户市值直接求和。在同时模拟 A股、B股、港股时，金额需要先区分币种才能正确表示。

此外，RiskGate 资金校验调用 `buy_fee(notional)`，撮合调用 `fee(side, amount, symbol)`。同一笔金额 `100000` 的港股买单，本轮执行得到费用分别为 `35.00` 与 `110.35`。这能说明两条代码路径不一致，不代表本轮重新核验了交易所费率。

实施：按 `账户 × 币种` 保存现金、冻结额和市值；费用预估、预占、成交结算都调用同一市场规则。默认分别展示 CNY/USD/HKD，合并资产只能使用明确标注时间与来源的汇率，保留原币金额。

手机保持独立本地练习场，通过构建时生成的规则 JSON、规则版本和共用样例与 Python 对齐，覆盖两端的整手、费用、T+1/T+0、价格精度。仅复制相同文案不能保证规则执行一致。股票每手数量等因标的而异的规则，需要证券主数据支持；缺失时展示实际采用的模拟假设。

### F05 · P0：PC 更新包不包含后端，更新失败也缺少完整回退

依据：`QuantDesk-App/发布.py:74`、`QuantDesk-App/pc/Launcher.cs:482`、`:900`。

调用现有 `pc_zip()` 在临时目录真实打包并读取 ZIP，结果：

```text
files=13
has_backend=false
has_backend_version=false
has_dependency_lock=false
has_frontend=true
```

包里有启动器、前端构建结果和手机页面，没有 `quantdesk/` 后端和后端版本文件。因此后端改动不能随这个包送达，后端版本读取也不会随包更新。当前替换是逐文件覆盖，失败时可能留下混合版本；缺失 `dist` 目前只发出警告。

实施：先定义“依赖已有环境的更新包”和“面向新电脑的完整安装包”两种交付合同。更新包必须覆盖本次声明支持的后端、前端、启动器、资源、版本元数据和依赖兼容信息，缺件直接停止发布。已有 `uv.lock` 与 `frontend/pnpm-lock.yaml` 应进入可重复构建流程。

新版本先放独立目录，校验文件清单后准备数据库备份与迁移；确认自有后端停止并释放文件，再切换版本并做就绪检查。失败恢复旧代码与匹配的数据库备份，旧版本目录保留到验收结束。SHA-256 继续校验完整性；独立的清单签名与版本单调性检查负责发布者身份和防降级，二者分别验收。

### F06 · P1：WebSocket 跨线程入队与丢事件需要可观察、可恢复

依据：`quantdesk/core/events.py` 同步分发；`quantdesk/api/ws.py:49`、`:55`。

事件在发布线程内执行回调，WS 回调直接操作 `asyncio.Queue`。虽然取得了 `loop`，并未使用它进行线程切换。队列满时只递增局部 `dropped`，客户端看不到缺口。

实施：跨线程通过 `loop.call_soon_threadsafe()` 调度到事件循环，再执行受容量控制的入队。行情按标的合并最新值；订单、成交与风控事件出现缺口时，客户端按游标补取或重读持久化快照。队列容量、积压、丢弃和重连状态进入诊断信息。还要限制待调度回调的积压，避免把无限队列转移到事件循环。

这属于代码与官方并发合同核对后的问题，本轮未做 WS 压力复现。Python 文档明确说明 [asyncio.Queue 不具备线程安全性](https://docs.python.org/3.11/library/asyncio-queue.html)，并给出[跨线程调度方法](https://docs.python.org/3.11/library/asyncio-dev.html#concurrency-and-multithreading)。

### F07 · P1：回测仍在服务进程执行策略，取消依赖策略主动返回

依据：`quantdesk/services/backtest_svc.py:283`、`:421`。异步队列的工作线程直接实例化策略并执行 `BacktestEngine.run()`，策略代码没有在这里进入独立进程；队列也没有容量上限。

实施：回测也使用每任务独立子进程；策略模块导入、构造、`on_init/on_bar` 都放进子进程，主进程只调度、接收进度和写入结果。先请求合作取消，超过期限后结束该任务进程，保留已提交分块并标明结果不完整。首版限制为单个并发任务、有限排队数，容量通过压测决定。

验收包括死循环、构造函数抛错、子进程异常退出、大量日志、取消与服务重启。任一任务失败不能使 API 卡住或带走交易编排。实时策略已有 supervisor/IPC 基础，应复用其进程管理经验；进程隔离也不应被描述成完整的文件系统安全沙箱。

### F08 · P1：Parquet 存储需要保护写入，并按查询区间裁剪读取

依据：`quantdesk/store/parquet_store.py:76`、`:96`。当前会直接覆盖目标文件；读取时先读完该标的周期目录内所有分区再过滤日期。

实施：每个分区串行执行读、合并、写；写到同目录临时文件，回读校验后用 `os.replace()` 替换正式文件。进程内锁与跨进程写入要采用统一协议，不能只保护一个调用方。读取先按年/月选择分区，再用现有 pyarrow 的列裁剪和过滤能力。

标准列继续保持 `dt/open/high/low/close/volume/amount`。来源、复权因子版本、抓取时间、数据哈希和校验状态存旁表或 manifest，避免把各家扩展字段塞进统一 K 线合同。

### F09 · P1：市场日历与价格规则需要明确证据，缓存要按字段刷新

依据：`quantdesk/services/watch.py:126`、`quantdesk/engine/riskgate.py:314`、`:335`。

`session_of()` 只用星期和时段，没有读取节假日日历；A股与港股还需要分别覆盖假日、半日市和临时休市。现有交易日历抓取使用 SSE，表中没有市场维度，需要与盯盘统一接线，避免普通工作日休市时仍自动外呼。

价格区间代码会根据 N/C 简称、价格大幅越过推算区间推断“本日不限”。这类启发式应保留证据与置信度；实盘应使用已验证的交易日规则和证券主数据，证据不足时按现有 fail-closed 原则处理。`_quote_row()` 还会将非空快照按整日缓存：价格、动态盘口与日级规则应分开 TTL，字段首次缺失也不能阻断后续补取。

验收：模拟两个市场的独立假日与港股半日市，自动路径外呼为零；手动 force 仍遵守限速与主机冷却。构造先缺字段后补齐、跨日、来源冲突、简称不规范的快照，逐项检查规则卡与执行结果一致。

### F10 · P1：回测可回看已经实现，可复现研究还缺少运行快照

依据：`quantdesk/engine/backtest.py` 的运行 config、`quantdesk/services/backtest_svc.py` 的结果明细。已有参数与成交记录，但未记录完整的策略源码快照、数据分区哈希、费用规则版本和环境摘要。

实施：每次运行冻结策略内容及哈希、参数、标的集合、时间区间、复权类型、数据版本、撮合配置、费用规则、软件版本与依赖锁摘要；派生报告从这份 manifest 读取事实。唯一 ID、实际运行时间等非确定字段单列，重复运行比较业务结果。

继续验证下一根 bar 成交的已有约定，并扩展同时间多标的权益聚合、跨周期未收盘 K 线可见性、停牌/涨跌停成交假设。财务因子按公告可得时间使用，证券池按当时可交易成员构造。前复权结果用于研究时，也要说明跨除权日期的成交与现金处理假设，避免将研究价格直接用于真实委托。

## 4. 建议实施顺序与任务卡

以下按一名熟悉项目的工程师估算，不含券商开通、真机等待及对外发布。每项先补能复现问题的测试，再改实现；完成后单独提交。任务名称是建议新增的工作项。

| 顺序 | 工作包 | 主要修改范围 | 必须交付的验收 | 初估 |
| --- | --- | --- | --- | --- |
| K01 | 确认最终校验、截止时间、通道绑定 | riskgate、trading、确认持久化记录 | F01 四种变化均不发出错误实盘委托；并发确认只执行一次 | 2～3 人日 |
| K02 | 账本作用域与版本化迁移 | models_db、db、repo、查询与对账 | 模式/账户隔离；旧库逐版本升级；来源未知记录不被自动成交回放 | 3～5 人日 |
| K03 | 原子结算、请求/回报幂等、资金预占 | repo、paper_broker、交易编排 | 写入每个阶段注入异常仍账目一致；重复请求/重复回报不重复记账 | 3～5 人日 |
| K04 | 多币种与规则同源 | 账本、matching、riskgate、PC/手机展示、构建资源 | 原币分账；两端同样例同结果；预估费用等于结算费用 | 3～4 人日 |
| K05 | 完整更新与失败回退 | 发布器、启动器、版本信息、迁移入口 | 老版→新版，后端行为与前端均改变；缺件阻断；故障恢复旧版 | 3～5 人日 |
| K06 | WS 线程切换、快照补偿、就绪诊断 | ws、事件连接、system 服务 | 后台线程发事件；慢客户端与断线恢复；缺口可见并能恢复一致状态 | 1～2 人日 |
| K07 | 回测任务隔离与运行 manifest | backtest_svc、runner、结果存储 | 死循环可终止；API 保持响应；相同快照重复运行结果一致 | 3～5 人日 |
| K08 | 数据写入、日历、规则证据 | parquet_store、calendar、watch、规则服务 | 并发写不丢行；替换失败原文件可读；休市零自动外呼；缺字段可补取 | 3～5 人日 |

依赖关系：K01 可先做；K02 为 K03/K04 的数据基础；K05 的数据库回退依赖 K02 的迁移合同。K06 可独立推进；K07/K08 完成后再做研究能力扩展。上述总量约 21～34 人日，应拆成多个可验收版本，不把全部内容承诺为一周交付。

## 5. 基础稳定后，最值得做的功能

### 5.1 规则选股与每日复盘工作台

复用现有 interop 规则，不新建另一套选股表达式。用户选择条件后，同时得到历史信号、当日候选、触发原因、缺失数据说明和板块导出。保存每日候选及人工观察记录，使第二天能检查信号有没有按规则出现。

首批围绕已有均线、MACD、RSI、量能规则提供少量模板，配置说明包括数据要求、触发条件和失败示例。与通达信、同花顺互操作继续保持同源求值。

### 5.2 研究报告与模拟跟踪对照

每份报告同时呈现基准、回撤、成本、换手、样本内/样本外结果、参数扰动及数据缺口。参数搜索必须记录搜索次数与候选全集，预留未参与调参的最终检验区间；先完成单策略研究，再扩大量化筛选任务。

回测转模拟只复用策略与参数；通过信号时间、委托时间、成交价格和费用的逐笔对照解释偏差。为模拟撮合提供“理想条件/受成交量约束”等明确配置，报告披露滑点、成交量占用和涨跌停假设；不要默认把零滑点、全 bar 成交量可用当成现实成交能力。

### 5.3 本地诊断与数据质量面板

健康信息区分存活与就绪：数据库可写、迁移版本、静态资源版本、策略进程、行情时间、限速等待、主机冷却、队列积压和最近对账结果。当前 `/api/system/health` 只返回基础状态，适合保留轻量探活，另补就绪与诊断接口。

行情显示来源、市场时间、接收时间、币种、复权口径和缺失字段；“多源一致”必须说明同一时点、同一字段与单位。单次抽样无冲突不能延伸为所有标的、所有时刻准确率 100%。港股内外盘、五档等单源数据继续如实标明。

诊断导出采用白名单，只包含脱敏状态与版本，不打包保险库、账号、token、资金目录或完整环境变量。本地写 API 与 WS 还应核对 Host/Origin 和会话约束；仅绑定回环地址不代替调用来源校验。此项为设计建议，本轮未做攻击复现。

### 5.4 交付体验与商业验证

先验证“陌生用户在干净 Windows 上安装 → 看行情 → 跑模板 → 查看持久化报告”的完整体验。现有 PC 版本仍依赖源码和 Python 环境，应先把产品形态写清，再决定是否采用已有栈允许的打包方案；新增构建工具另行说明依赖与维护成本。

早期邀请少量用户按统一任务试用，记录首次成功所需时间、卡住原因、每周复盘次数和报告使用情况。商业能力优先围绕安装维护、研究报告、规则模板、数据与通道接入服务验证需求；涉及第三方行情分发时单独确认对应授权范围。收益高低不作为软件工程质量的替代指标。

## 6. 性能与发布验收目标

这些是下一阶段拟采用的目标，需要记录测试机配置后测量，本轮没有宣称达标。

| 场景 | 测量与目标 |
| --- | --- |
| 本地缓存命中的自选列表 | 100 标的合成负载，API P95 ≤150ms；外网取数耗时另列 |
| 盯盘刷新与页面操作 | 输入/点击反馈目标 ≤100ms；同一请求不重叠，旧请求可取消或丢弃；页面隐藏时降频 |
| 长时间运行 | 用录制或合成行情运行 6 小时，检查内存、线程、监听器、队列和 DB WAL 是否持续增长 |
| Parquet 查询 | 对相同标的“近一月/多年”分别记录读取分区数、耗时与峰值内存，验证分区裁剪收益 |
| 回测取消 | 合作取消与强制终止分别计时；死循环不阻塞 API，建议在 3 秒强制终止窗口内收口 |
| 更新与恢复 | 中文路径、文件占用、磁盘不足、缺 dist、旧库、坏哈希、迁移失败、首次启动失败逐项演练 |
| 状态恢复 | 断 WS/重启 API 后，订单与账户视图最终和持久化快照一致；关键事件缺口有明确信号 |

负载与故障测试使用假行情、临时目录和假券商；真实公开接口只用于有节奏的字段核对，继续遵守限速、主机冷却及休市规则。

每次发布应保存一份机器可读验收清单：Git commit、后端/前端/启动器/安卓版本、schema 版本、依赖锁摘要、产物哈希、测试摘要和未验证项。现有 `pyproject.toml`、`frontend/package.json` 仍是 `0.1.0`，运行时与安卓为 `1.2`，应定义并生成一致的产品版本来源，避免各处手改。

建议发布流程：锁定依赖构建 → 离线测试 → 临时目录端到端 → 旧库迁移/回退 → 更新包完整性 → 干净环境安装 → 手动抽样核对 → 记录结果。真实券商委托的验收保持独立用户在场步骤。代码签名可建立发布者身份，但不应承诺一定消除系统信誉提示。

备份使用 SQLite Online Backup API；Parquet、规则和策略快照另带 manifest。SQLite、Parquet 与配置若需形成一致恢复点，应协调写入或冻结相应快照，单独备份 SQLite 不等于整个应用一致备份。恢复必须在新目录演练，并核对账本和回测记录。DPAPI 密文与 Windows 用户身份绑定，跨机器迁移应明确重新录入凭据的流程。参见 [SQLite 在线备份说明](https://www.sqlite.org/backup.html)。
